# TASK-0030 — 用户管理基础（单任务串行）

## 背景与顺序
TASK-0029 已 completed，local main 已同步、后端运行、模块审计可用。现在开始用户管理基础。用户明确要求“继续吧，别冲突了”：严格单任务串行，勿与其他任务并发或触发后续任务。后续模块授权、注册开关/审核分别另立任务，不在本任务实现。

## 目标
在现有 FastAPI SQLAlchemy/SQLite/PostgreSQL、owner/admin/viewer RBAC、session/CSRF 基础上，提供安全的管理员用户管理 MVP。先阅读 auth model、routes、policy、现有迁移、前端布局、测试和 .coordination/PROTOCOL.md。

### 范围
1. 管理员后台用户列表：分页、最小必要字段（ID/用户名/角色/启用状态/创建时间等已有字段），搜索如易于安全实现；不得暴露密码哈希、会话、CSRF、敏感信息。
2. 仅 owner 或 users.manage 权限（严格遵循现有权限矩阵）可创建用户、修改允许的角色/启停状态；viewer/匿名拒绝，服务器端校验，CSRF+来源保护，拒绝用户自我降权/禁用及最后一个有效 owner 被移除。普通用户账号默认无管理权限。
3. 管理员创建用户：仅由受授权者创建，初始密码以安全输入处理（不回显、不写日志、不上传 GitHub/测试快照），沿用现有 Argon2id 密码处理与校验；不添加默认密码，不自动注册。不要实现邮件重置或公开注册（另任务）。
4. 前端独立“用户管理”页面，权限不足时不可操作，合理的确认与成功/失败反馈，避免重复身份/导航区域。移动端适配。
5. 如需迁移，必须新增可审查 Alembic migration，绝不在用户真实开发 SQLite 上自动 upgrade/downgrade；必要时仅用临时测试库。优先复用已有 auth_users 表。避免无必要依赖。
6. 测试：owner/admin/viewer/匿名矩阵、CSRF、非法输入、重复用户名、角色提升、保护最后 owner、账号启停、数据库持久化/事务回滚、响应脱敏；Node/build/Chrome fixture 适当覆盖；PG CI 适用时覆盖。
7. 独立分支+PR，不自动合并，不部署、不重启真实服务、不读用户真实表内容或凭据；只读核实 schema 元数据即可。按 .coordination/PROTOCOL.md 写 .coordination/status/TASK-0030.json。

## 边界
- 不实现用户级模块授权、公开注册、注册审核、密码重置/找回、邮件发送、动态插件安装。
- 不修改真实开发 SQLite 用户/角色/密码；不操作生产。
- 如果发现权限语义需要变更或 migration 有破坏性，先停下来在 status 说明设计与阻塞，不擅自改变安全策略。
- 不编辑其他 TASK 状态，不自行创建或发布 TASK-0031；等待 ChatGPT 复核和后续串行调度。

## 验收
独立 PR + CI 测试，管理员可安全创建和管理用户；默认关闭注册，普通用户不会自动获得管理权限。
