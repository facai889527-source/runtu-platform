# TASK-0015 — RBAC 授权与管理 API 安全边界（不开放业务写操作）

## 背景
TASK-0014 PR #14 已实现首阶段管理员身份认证（Argon2id、DB hash session、CSRF/Origin、限流、本地初始化、审计及登录UI），报告 37 Python/10 Node 测试通过，但未进行 PostgreSQL 在线验证。用户要求继续开发。此任务重点是**认证之后的授权**，确保未来工具模块写操作具备可复用、默认拒绝的保护层；不要急于开放管理写接口。

## 安全设计与实现
1. 先审阅真实 #14 认证模型、session、审计、Alembic 0002、FastAPI 依赖、模块路由挂载及测试，写清威胁模型和权限模型。**默认拒绝**，所有受保护管理操作必须在服务端鉴权；前端显示不是权限边界。
2. 设计最小但可扩展的 RBAC：初始内置角色 `owner`、`admin`、`viewer`（或给出更合适的明确命名），权限粒度至少区分 `platform.read`、`module.read`、`module.manage`、`users.manage`、`audit.read`。不得因 viewer 能看公共 GET 就自动获得管理权限。明确 owner 特权、admin 范围和最小权限原则。
3. 将角色/授权状态持久化到数据库并提供 Alembic 迁移，保证现有本地初始化管理员的安全升级路径（避免旧管理员升级后失去所有权，也避免匿名获得管理权限）。SQLite测试兼容；明确 PostgreSQL 风险与数据回滚策略。若 RBAC 复杂度过高，先提供固定内置角色和可测试的角色检查，不创建未经授权的动态授权编辑 API。
4. 提供可复用 `require_permission("...")` / `require_role(...)` 等依赖或等效安全检查；正确处理匿名401、已登录无权403、禁用/撤销/过期session401。未知权限必须拒绝，不能默许。
5. 提供最小**只读**受保护管理端点，例如 `GET /api/admin/me` 返回当前角色和明确的权限列表；如有审计只读列表端点，必须要求 `audit.read` 且严格分页/字段白名单/敏感字段清理，不得暴露密码哈希、token、cookie、IP原文等。不要新增用户创建、角色修改、模块启停、配置保存、删除或其他业务写端点。
6. 公共 `/api/health`、`/api/modules`、`/api/modules/{id}` 的既有只读契约不变。审查模块动态 router 注册的权限边界，确保未来插件不能绕过平台管理路由鉴权；若发现无法安全保证，明确 blocker，先做测试或设计而非冒险宣称隔离完成。
7. 前端：登录后显示服务端返回的真实角色/权限摘要（可在设置页或账户区域），未登录显示清楚的受限状态；没有权限的管理功能不可假装可用。保持现有 UI、Vue3+JavaScript、导航/响应式，不存敏感会话数据于 localStorage。
8. 更新 `docs/AUTH_SECURITY.md`、新增 `docs/RBAC_DESIGN.md`：角色权限矩阵、401/403语义、服务端依赖用法、迁移/回滚风险、后续安全写 API 的 CSRF/Origin/审计强制规则。不要把本任务描述为生产可用的完整权限平台。
