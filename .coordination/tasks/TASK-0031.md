## 目标
Owner 可按用户授予/撤销可使用的业务模块权限；用户只能看到和调用自己被授予且平台已启用的业务模块。保留现有 owner/admin 平台管理权限、会话、CSRF、审计与现有模块管理 API 行为；不能将模块访问授权等同于 users.manage/module.manage。

## 设计先行
先审查 backend/auth/policy、模块 registry、ModuleManagementService、模块 API、前端路由/导航、auth users 表与 0004 schema。写简短设计 docs/USER_MODULE_ACCESS.md，明确权限矩阵：owner 全平台管理；admin 仍按现有权限管理模块但不能擅自管理用户授权；viewer/普通用户仅获授权的业务模块使用权。特别区分“模块目录元数据的可见性”与“实际业务 API 可调用”，避免破坏已有公开 API 及 DemoModule；如果现有 Demo API 是公开的，禁止直接以此任务悄悄更改公开契约。遇到需要用户产品决策的访问语义冲突，写 status blocked 并说明，不要猜。

## 实现
1. 复用现有 users.manage（owner 专属）作为授权编辑权限，服务端事务校验 owner active 和最新角色；用户可读自身模块授权摘要，Owner 可读取/修改目标用户授权。默认新用户零个业务模块授权（deny by default）。
2. 数据持久化以最小 Alembic 新迁移实现 user↔module 授权关联（或现有模式足以支持时复用）；SQLite/PostgreSQL 都必须可迁移/回滚于临时测试数据库；不要自动迁移真实开发库。
3. 平台全局禁用模块时，授权不能绕过禁用；不存在模块、不可授权的核心系统模块、未知用户等明确拒绝。重复授权幂等或版本冲突明确；并发写入、审计、回滚与会话状态检查，避免 TOCTOU。不要授予模块管理或管理员权限。
4. Owner 用户管理页可编辑每个用户的业务模块访问权限；移动端可用，状态、失败和确认提示清楚。用户自己的工作台只显示获授权的业务模块入口，避免多余导航；服务端权限为最终权威。
5. 在明确存在可授权的受保护业务 API 时集成后端 enforcement；若当前仅有 demo/公开 API，先实现权限基础与隔离测试及适当授权示例，不要虚构安全保护已覆盖所有未来业务接口。对未来模块作者提供 require_module_access(module_id) 类似可复用后端依赖/接口，明确调用方式。
6. 测试 owner/admin/viewer/匿名、未授权/已授权、全局模块禁用、用户停用、非法模块、重复/并发/回滚、审计及敏感数据不外泄；前端单测/build、PG CI 和隔离浏览器夹具，更新文档。
7. 不实现公开注册、注册审核、密码重置、邮件、动态 ZIP 插件安装。绝不读取/改写用户真实本地 SQLite、真实账户、凭据或模块设置；不重启本地服务，不部署。
