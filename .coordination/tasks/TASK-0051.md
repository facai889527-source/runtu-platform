# TASK-0051 — Per-account Telegram binding and private notification routing

Product decision confirmed by user: EACH ACCOUNT independently binds and configures its own Telegram notifications. Supersedes TASK-0050 platform-wide singleton semantics. Telegram is the ONLY messaging channel. Preserve TASK-0050 registration/settings cleanup and PR28 work.

Requirements:
1. “消息设置” visible to every authenticated user (owner/admin/ordinary), with /api/me/notifications or equivalent self-service endpoints; never expose or mutate another user's configuration through user-supplied IDs. Back-end authorization mandatory. Anonymous denied. Owner/admin may configure their own Telegram, NOT a global shared Chat ID. Registration alerts go only to eligible owner/admin recipients who opted in; tool events only to the specific tool user, respecting tool permissions and preferences.
2. Decide safe binding UX: prefer shared platform-managed Telegram bot with per-account Chat ID securely VERIFIED via one-time challenge/deep-link /start token tied to logged-in user, short TTL, single use, unlink/rebind and revoke, or another robust ownership-proof handshake. Users should not need to create their own bots. Never accept arbitrary Chat ID as “verified” or send sensitive messages to unverified destinations. A platform bot token stays server-side in environment, never appears in API/frontend/logs. Document bot setup and polling/webhook callback security, replay protection, concurrency and group/channel policy. If full verification cannot be completed safely, stage behind disabled feature and report blocker, never falsely claim binding is secure.
3. Per-user settings persistence: bound Telegram identity/chat, verified state, enabled toggle, event subscriptions. Migration on disposable DB only, with explicit plan for TASK-0050 singleton migration and safe conversion; DO NOT silently copy legacy global Chat ID into all user accounts, and do not leak shared preferences. Registration approval event routes only to eligible privileged accounts, dedupe per recipient/event; tool outcomes only when actual task events exist, otherwise UI shows not yet supported. No fake event sources.
4. Telegram sending: fixed HTTPS Telegram API destination, bounded timeouts and queue, rate limit test messages, retry/expiry policy with no sensitive token logging, no business transaction rollback on delivery failure, avoid user enumeration and cross-user notification leaks. Secure test-send to the requesting user's VERIFIED chat only. Handle disabled/deleted users, revoked sessions, role changes, stale binding, blocked bot and failed sends.
5. UI: elegant self-service Telegram connection state, Connect Telegram CTA, clear step-by-step pairing, enabled switch, supported event preferences, test send, disconnect/reconnect, error/loading/success feedback. Use existing premium UI and clean obsolete singleton admin-only settings/components/CSS and migration assumptions. Responsive 1440/390/360, keyboard/ARIA and reduced motion.
6. Comprehensive tests: account A cannot read/change/send to B; ordinary user access; owner/admin registration routing; unverified chat blocked; one-time binding token replay/expiry; duplicate event dedupe; disabled user; backend security; frontend build and browser. No real Telegram token/sends, no real DB migration, service restart, merge or deployment. Work safely on PR28 branch only if clean, avoid conflict.
