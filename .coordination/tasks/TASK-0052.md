Authoritative product decisions:
- Every account, including owner, starts completely UNBOUND, no bot selection, Telegram identity, chat, group, destinations, subscriptions or enabled notification. NO automatic assignment of shared bot. Notifications default OFF. User must actively bind.
- Every account can choose either (A) platform PUBLIC bot configured by owner or (B) their OWN Telegram Bot Token. Users can switch only via explicit action; securely clean/revoke previous binding/targets. Individual token must be securely encrypted at rest with operator-managed encryption key, never returned/logged in plaintext; fail closed if secure secret storage unavailable. Shared bot token also protected. Owner has FULL authority to view/manage/change/unbind ANY account's notification configuration (including sensitive settings via secure authorized operations); admins and ordinary users can manage ONLY themselves. Do not conflate Telegram secret management with ordinary profile permissions.
- Public bot MUST first establish account's Telegram identity by user-initiated PRIVATE /start one-time challenge handshake. No arbitrary Chat ID proof. Then available group list for ordinary users/admins is INTERSECTION: groups discovered for the public bot AND groups in which their verified Telegram user is currently a member. Check getChatMember (with necessary bot admin privileges) and fail closed on unknown/error. Owner sees ALL public-bot-discovered groups, regardless of membership. Enforce visibility and authorization on backend, selection AND sending; never leak all groups to non-owner. Recheck membership/permissions at send time or conservative expiry. Bot must also be a current member and able to send.
- Personal bot: user supplies token, verify with Telegram getMe and safely establish ownership/control. Discover groups on bot-visible updates: my_chat_member and accessible group messages/commands/updates; Telegram Bot API CANNOT enumerate all historical groups. Show discovered groups belonging ONLY to that account's bot. Ensure webhook/getUpdates offset handling doesn't collide with other deployments or a bot already using webhook. Document needed group admin/privacy permissions and partial-discovery behavior. For private destinations require verified private /start handshake even with personal bot.
- Multiple destinations per account, including private chat AND several groups simultaneously; selectable, individually removable. Event-specific opt-in preferences where actual event source exists, no fabricated tool notifications. Ensure per-event dedupe per destination, bounded queue/timeout and no cross-account leaks.
- Disconnect must DELETE/CLEAR bot selection, bound Telegram user identity, chat, group target selections, event subscriptions, notification enabled status, pairing challenges, and revoke active routing; return pristine unbound state. User disabled/role or tool permissions lost -> stop corresponding deliveries.
- UI polished, accessible, mobile, unbound initial empty state with explicit buttons "使用公共 Bot" and "绑定个人 Bot", proper discovery and membership status, selected multi-target chips, test-send only to verified authorized destinations, robust error states. No other notification channels.
- Security: owner/admin/user isolation, token encryption/rotation, webhook authentication, one-time challenge TTL/replay, group member authorization, group visibility, group updates, race conditions, CSRF/Origin, test-send rate limiting, SSRF-resistant fixed Telegram HTTPS API, secrets never leaked.
